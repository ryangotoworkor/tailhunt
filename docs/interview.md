# 面试题

按面试里常见的七类分组，共二十八题。每题先给一句话答案，再展开，最后是追问和答法。
所有数字都是这个仓库实测的（本机 colima 四核共享，多轮取中位数），告警历史是**合成数据**。简历上的数字是公司里的结果，在最后一组单独讲，不和仓库的数字混用。

## 项目概述

### 讲讲这个项目（一分钟版）

**一句话答案**：一个酒店房态搜索的六服务 Go 系统，用来完整演练「p99 间歇性飙高 → 定位到数据库连接池耗尽 → 分层修复 → 证明修好了 → 用告警历史数据决定优先级」这一整套流程。

**展开**：网关、搜索、库存、报价、画像、风控六个服务，库存服务独占 Postgres，连接池上限六条。锁房事务在 `FOR UPDATE` 之后调了报价服务，报价一慢，连接就被攥住，搜索在 database/sql 里排队。我用 OpenTelemetry trace、`sql.DBStats` 和 `pg_stat_activity` 三个信号定位，修复分四层：拿连接超时、舱壁、把报价挪出事务、报价超时加熔断。每层都有一个关掉就变红的测试。同样的故障下，搜索 p99 从一万毫秒（被网关十秒超时截断）回到 5.9 毫秒。另外用 DuckDB 跑 Spark 风格的 SQL、pandas 做后处理，分析半年合成告警数据，结论是这类故障按总影响排第一，并把排查方法写成了 runbook。

**追问**：为什么要做六个服务，一个不行吗？
答：尖峰常常不在你盯着的那一跳。扇出结构让「顺着 trace 找」变成必要步骤；单服务的话看一眼 CPU 就知道了，练不到定位。

### 这个项目里你觉得最有价值的一部分是什么？

**一句话答案**：「能失败的对照」：每一层修复都配一个开关，关掉它，对应的测试必须变红。

**展开**：绿灯有两种成因，一种是对的，一种是测试根本测不到。`TAILHUNT_SABOTAGE=<层>` 在测试背后关掉那一层（[config.go#sabotage](../internal/inventory/config.go#sabotage)），[failing-controls.sh#failing-controls](../scripts/failing-controls.sh#failing-controls) 要求「关掉就红、打开就绿」，十组全部符合预期。分析部分也有：把排名改成按次数，钉住头号原因的测试必须红。

**追问**：这个脚本自己出过问题吗？
答：出过。第一版的「干净」组在 bash 3.2 上根本没跑，见 [problems.md 第 3 题](problems.md#q03-bash32-empty-array)。因为判据要求看到 PASS，它红了而不是悄悄变绿。

### 教学模式是怎么做的？为什么不是前端动画？

**一句话答案**：后端真的在跑这次排查，前端每秒轮询状态，每一步停下来等「下一步」。

**展开**：`/api/learn/runs` 启动一个状态机（[learn.go#stage-alert](../internal/gateway/learn.go#stage-alert) 起九个阶段），真的注入故障、等 Prometheus 告警触发、从 Jaeger 取最慢的 trace、读 DBStats 和 pg_stat_activity、切修复、再测量。页面上每个数字都是这次运行的真实返回。e2e 从界面点一遍，断言阶段依次亮起、数据出现、源码链接指向的行真实存在。

**追问**：每次跑出来的数字一样吗？
答：不一样，这正是目的。告警触发时间、峰值 p99 每次都有差异，但结构性结论（等待都在 acquire、InUse 顶满、修复后等待为零）每次都成立，e2e 断言的是这些。

## 设计取舍

### 为什么用 database/sql 而不是 pgxpool？

**一句话答案**：题目就是 database/sql 的池子，它的 `DBStats` 是 Go 服务最常见的连接池指标。

**展开**：pgxpool 也有 `Stat()`，等待指标更细。但大量生产 Go 服务用的是 database/sql + 驱动，`SetMaxOpenConns`、`WaitCount`、`WaitDuration` 是值班时真正能看到的东西。驱动用的是 pgx 的 stdlib 适配（[db.go#pool-open](../internal/inventory/db.go#pool-open)）。

**追问**：MaxOpen 为什么设六？
答：故意设小，让事故在笔记本上用每秒几十个请求就能复现。线上要按「数据库能承受的连接数 ÷ 实例数」来定，并留余量给诊断和后台任务。

### 为什么要显式调用 db.Conn() 拿连接？

**一句话答案**：为了让「等连接」在 trace 里成为单独一段。

**展开**：`QueryContext` 内部先拿连接再发查询，等待时间藏在查询 span 里，看起来像 SQL 慢。[pool.go#pool-acquire](../internal/inventory/pool.go#pool-acquire) 显式拿连接，包一个 `db.pool.acquire` span、记直方图、写进请求日志的 `db_wait_ms`。事故时 trace 里这一段占了 100%，真正的查询零点二毫秒。

**追问**：多一次 Conn() 有开销吗？
答：几乎没有，它就是 QueryContext 内部做的那一步，只是拆出来了。代价是调用方要记得 `Close()` 把连接还回去。

### 舱壁和拿连接超时，为什么两个都要？

**一句话答案**：超时让失败变快，舱壁让搜索不失败；作用不同。

**展开**：只开超时时池子依然满，测试里搜索 p99 82 毫秒、但错误率八成五：它只是不让网关的 goroutine 陪着排几秒。舱壁限制锁房最多占六条里的两条（[guard.go#bulkhead](../internal/guard/guard.go#bulkhead)），搜索永远有四条可用，p99 3.0 毫秒、零错误，代价是锁房出现 429。两个都开是纵深防御：根因修了以后，它们防的是下一个没预料到的慢路径。

**追问**：舱壁为什么不用 SetMaxOpenConns 拆两个池子？
答：也可以，两个 `*sql.DB` 各自限额。信号量更灵活：可以按路径限、运行时调，不用多维护一组连接。缺点是要保证槽位只包「持有连接」的那段，第一版就包错了，见 [problems.md 第 2 题](problems.md#q02-bulkhead-scope)。

### 为什么根治是把调用挪出事务，而不是加大连接池？

**一句话答案**：加连接只是把排队从应用挪到数据库，下游再慢一点又满了。

**展开**：每秒二十五个锁房、每个攥三百毫秒，平均要七点五条连接。加到十条能撑住这个流量，但 quote 慢到六百毫秒就又不够，而且 Postgres 的连接是进程，越多越贵。挪出事务后连接只被占几毫秒（[hold.go#hold-fixed](../internal/inventory/hold.go#hold-fixed)），容量和下游延迟解耦了。

**追问**：价格和库存的一致性怎么保证？
答：价格只取决于酒店、日期和会员等级，跟剩余房量无关，所以先报价不影响正确性。扣库存用一条带条件的 `UPDATE ... WHERE rooms_left > 0 RETURNING`，检查和扣减是原子的。

### 熔断器为什么不是主角？

**一句话答案**：这次的问题不是 quote 失败，而是 quote 慢；熔断只在连续失败时起作用。

**展开**：quote 慢三百毫秒但都成功，熔断器一直是 closed。它防的是 quote 彻底卡死：测试里 quote 卡两秒，每次锁房八百毫秒超时，连错五次后第六次立刻被拒绝（`TestFix_QuoteGuardBoundsHoldLatencyAndOpensTheBreaker`）。

**追问**：熔断阈值怎么定？
答：这里是连续五次、冷却三秒，演示用。线上一般按错误率加最小请求数，冷却时间参考下游的恢复时间，并且半开时只放一个探测请求，代码里就是这样做的。

### 为什么用 DuckDB 而不是 Spark？

**一句话答案**：数据量是笔记本级别，DuckDB 一秒出结果；SQL 按 Spark 方言写，可以直接搬。

**展开**：三千条告警、十万行请求日志，起一个 Spark 集群没有意义。[00_dialect.sql](../analysis/sql/00_dialect.sql) 用两个 macro 让 DuckDB 认 `percentile_approx` 和 `unix_timestamp`，所以 SQL 本身是 Spark SQL / HiveQL 的写法，换到 `spark.sql(...)` 只要改建表。

**追问**：哪些地方搬到 Spark 要注意？
答：`time_bucket` 在 Spark 里要换成 `window()` 或 `floor(unix_timestamp/10)`；`read_json` 换成 `spark.read.json`；`percentile_approx` 在 Spark 里是近似值，结果会有很小的差异。

### 请求日志为什么自己写 JSON Lines，不用 OTel logs？

**一句话答案**：分析要的是一行一个请求、带 trace_id 和 db_wait_ms 的宽表，JSON Lines 最直接。

**展开**：[reqlog.go#reqlog-line](../internal/obs/reqlog.go#reqlog-line) 七个字段，网关和 inventory 的同一个请求靠 trace_id 对上，SQL 一个 join 就能把「端到端耗时」和「等连接时间」放在一行（[60_requestlog.sql#sql-trace-join](../analysis/sql/60_requestlog.sql#sql-trace-join)）。

**追问**：日志会不会把磁盘写满？
答：带缓冲写、每秒刷一次，单文件超过六十四兆轮转一次。线上会交给日志采集器，并且对健康检查和 metrics 抓取不记日志，代码里已经这么做了。

## 正确性和故障

### 同一间房被两个人同时锁会怎样？

**一句话答案**：不会超卖。修复前靠 `FOR UPDATE` 行锁，修复后靠一条带条件的 UPDATE。

**展开**：`UPDATE ... SET rooms_left = rooms_left - 1 WHERE ... AND rooms_left > 0 RETURNING` 在 Postgres 里是原子的，两个并发请求只有一个能减到零，另一个拿到零行，返回 409。`TestHoldOnTheLastRoomThenSoldOut` 在 legacy 和 fixed 两种模式下都跑。表上还有 `CHECK (rooms_left >= 0)` 兜底。

**追问**：锁房以后客人不付款呢？
答：hold 带过期时间，后台任务每十秒用一条 CTE 语句把过期 hold 标成 expired 并把房间加回去（[sweeper.go#sweeper](../internal/inventory/sweeper.go#sweeper)），一条语句就是一个事务，中途崩溃不会只做一半。

### 报价服务彻底挂了会怎样？

**一句话答案**：锁房八百毫秒超时失败，连错五次后熔断，直接拒绝，不占连接。

**展开**：修复后报价在拿连接之前，所以报价再慢也不碰连接池，搜索完全不受影响。锁房本身会失败，这是正确的：拿不到价格就不应该锁房。

**追问**：能不能用缓存的价格？
答：可以做降级，但要产品确认。价格是要给客人付款的，用旧价格可能是资损；这个仓库选择失败而不是猜。

### 进程在事务中间崩溃会怎样？

**一句话答案**：Postgres 发现连接断开，回滚事务，行锁释放。

**展开**：锁房的扣库存和插 hold 在一个事务里，要么都成功要么都没有。清理任务是单条语句。唯一需要注意的是 legacy 路径里事务开着去调网络，如果应用卡住而不是崩溃，事务就会一直开着，这正是 `idle in transaction` 的危险：可以用 Postgres 的 `idle_in_transaction_session_timeout` 兜底。

**追问**：这个参数为什么没在仓库里打开？
答：打开它会让 legacy 演示里的事务被数据库杀掉，事故的样子就变了。线上我会设，比如三十秒，作为最后一道防线。

### 请求被网关超时取消了，下游还在跑吗？

**一句话答案**：不会一直跑：context 一路传下去，inventory 拿连接的那一步会因为 context 取消而返回。

**展开**：请求日志里 inventory `GET /availability` 有约百分之一点七的错误，就是网关十秒超时取消后，inventory 在 `db.Conn(ctx)` 里收到取消、返回 503。不传 context 的话，排队的请求会在客户端已经放弃之后继续占资源。

**追问**：超时应该怎么层层设置？
答：越往下越短：网关十秒、搜索拿连接八十毫秒、锁房报价八百毫秒、查询两秒。下游的超时比上游短，上游才有时间做降级和返回错误。

### 你遇到过最难排查的问题是什么？

**一句话答案**：修复上线后看板上 p99 没降，最后发现是统计口径错了，不是修复没生效。

**展开**：修复后连接池等待已经是零，p50 正常，只有 p99 还是九秒。两个信号矛盾，我怀疑口径：窗口按请求结束时间分桶，把修复前就在排队、修复后才结束的请求算进了「修复后」。改成按开始时间分桶，p99 从 7.62 秒降到 10.1 毫秒。完整过程见 [problems.md 第 7 题](problems.md#q07-window-by-finish)。

**追问**：还有别的吗？
答：等价性测试抓到旧排序代码的前缀怪癖（[第 4 题](problems.md#q04-rank-prefix-quirk)），演练中 Jaeger 自己 OOM（[第 5 题](problems.md#q05-jaeger-oom)），性能脚本因为标签里的空格算错分母（[第 6 题](problems.md#q06-awk-label-space)）。

## 扩展

### 流量放大十倍，瓶颈在哪？

**一句话答案**：先是 Postgres 连接数和锁房的写入，然后是网关。

**展开**：搜索是读，可以加只读副本、加缓存（房态允许秒级陈旧）。锁房是写，每次一条 UPDATE 加一条 INSERT，十倍就是每秒两百五十个写事务，单实例 Postgres 能扛，但连接数要算清楚：实例数 × MaxOpen 不能超过 `max_connections`，这时要上 PgBouncer 做事务级连接复用。

**追问**：上了 PgBouncer，`idle in transaction` 的问题还在吗？
答：还在，而且更隐蔽：事务级池化下，一个攥着事务的客户端会独占一条服务端连接。所以根治必须是「事务里不做网络调用」，中间件解决不了。

### 一百倍呢？

**一句话答案**：库存要按酒店分片，锁房异步化。

**展开**：按 hotel_id 分片，单个分片的热点酒店用排队或者预留库存块（每个实例先领一批房，用完再领）。搜索走专门的读模型（例如定期刷新的倒排索引），不直接查交易库。告警也要按分片聚合，否则噪音会成倍增加。

**追问**：预留库存块有什么问题？
答：会出现「这台实例上没房、那台还有」的碎片，以及实例挂掉时领走的房要回收，需要租约和超时归还。

### 压测数字能直接外推到生产吗？

**一句话答案**：不能。能外推的是结构性结论，不是绝对值。

**展开**：本机 colima 四核和别的项目共享 CPU，所以三轮交替跑、取中位数，表里同时给出每一轮。修复前 p99 三轮都是一万毫秒左右（被十秒超时截断），修复后三轮是 9、6、6 毫秒。能外推的是「修复后 p99 和健康基线同一量级、等待为零」，而不是「5.9 毫秒」这个数。

**追问**：生产上怎么验证？
答：灰度：先在一部分实例上打开开关，对比两组的 p99 和 DBStats；然后做一次受控的故障注入（让报价变慢），确认新代码下连接池不再饱和。

## 测试

### 你怎么证明修复是对的？

**一句话答案**：先有一个必须复现事故的测试，再有每层一个的修复测试，再用失败对照证明这些测试是活的。

**展开**：`TestIncidentReproduces_LegacyHoldsStarveAvailability` 在进程内用真 Postgres、六条连接、慢三百毫秒的报价桩，复现出 p99 三秒多；如果它复现不出来，后面所有「修好了」都不可信。然后四个测试各只开一层（[incident_test.go#test-fixed](../internal/inventory/incident_test.go#test-fixed)）。最后 `failing-controls.sh` 逐层破坏，十组都符合预期。

**追问**：这些测试慢吗？
答：每个约六到八秒，全套 inventory 测试四十秒左右。`-short` 会跳过负载型测试，CI 里完整跑。

### 测试里的阈值是怎么定的？会不会在 CI 上抖？

**一句话答案**：阈值和现象之间留了一个数量级以上的余量。

**展开**：修复后房态 p99 实测三到七毫秒，阈值是一百毫秒；修复前是三四千毫秒，阈值是三百毫秒。抖动远小于这个差距。依赖版本都钉死了：Go 1.27.4、postgres:16-alpine、Python 依赖精确版本。

**追问**：如果 CI 机器特别慢呢？
答：修复后的路径不排队，慢机器只会让每个请求慢一点，不会到一百毫秒；修复前的路径是排队，机器越慢越明显。所以阈值方向是安全的。

### 告警分析的结论怎么验证？

**一句话答案**：生成器埋了答案，测试不经过 SQL 直接从原始数据算真值，再和 SQL 的结果比。

**展开**：生成器另外写了一份 `alerts_truth.csv`，SQL 从不读它。测试检查：头号原因一致（[test_alerts.py#test-top-cause](../analysis/tests/test_alerts.py#test-top-cause)）；按时间关联估出的噪音率 55.0% 和真值 57.8% 差距在三个点以内；归因到原因的告警九成以上正确；朴素排名确实指向别处。

**追问**：用合成数据，结论有意义吗？
答：结论本身是被设计出来的，所以它证明的是**方法**能把埋下的答案找出来，而不是「现实中连接池最重要」。这一点 README 和报告里都写明了。

### 前端怎么测？

**一句话答案**：Playwright 从界面点一遍真实后端。

**展开**：e2e 登录、点「提交样例」，九个阶段依次等到 done，每一步断言真实数据出现（告警名、trace 里有 acquire、InUse 等于 MaxOpen 等），检查源码链接的格式，并且打开本地文件确认链接里的行号存在。另有面试题、日常问题标签页的展开测试。

**追问**：源码链接的行号会不会过期？
答：行号从不手写。`learn_anchors.mjs` 扫描 `@learn` 注释生成 anchors.json，`check_anchors.mjs` 在 CI 里检查生成文件没过期、每个引用都存在、文档链接的文件和锚点所在文件一致；链接里用的是构建时的 commit，不是 main。

## 系统设计延伸

### 上生产还缺什么？

**一句话答案**：配置中心、Alertmanager、PgBouncer、SLO 和发布流程。

**展开**：运行时开关现在是 HTTP 接口，生产上应该走配置中心并有审计。告警只到 Prometheus 这一层，没有 Alertmanager 的分组、抑制和 `repeat_interval`。pprof 和 admin 接口直接暴露在服务端口上，生产要放内部端口并鉴权。还有 `idle_in_transaction_session_timeout`、连接数规划和 SLO（例如搜索 p99 三百毫秒、月度错误预算）。

**追问**：admin 接口有鉴权吗？
答：经过网关的有（JWT、oncall 角色）；各服务自己的 `/admin/*` 和 `/debug/*` 没有，只靠在内网。这在 README 的局限里写了。

### 换成 AWS 怎么部署？

**一句话答案**：服务上 ECS 或 EKS，Postgres 上 RDS，前面加 RDS Proxy，观测换成托管服务。

**展开**：RDS Proxy 相当于托管的连接池，能缓解实例数增加带来的连接数问题，但同样救不了事务里调网络。trace 可以用 ADOT 导到 X-Ray 或继续用 Jaeger，指标用 Amazon Managed Prometheus 和 Grafana。告警数据分析可以把日志落 S3，用 Athena（Presto SQL）或 EMR 上的 Spark 跑同样的 SQL。

**追问**：RDS 上怎么看 pg_stat_activity？
答：一样能查；另外 Performance Insights 会按等待事件聚合，`Client:ClientRead` 高就是同一个信号。

### 告警规则在生产上你会怎么改？

**一句话答案**：页面告警只留症状类，资源类降级成 ticket，并按分析结果去重。

**展开**：`SearchP99High` 是用户症状，留作 page；`InventoryDBPoolSaturated` 是原因，作为 ticket 并在 page 里附带。按分析，它每次事故平均响六次多，要加 `for` 和 `repeat_interval`。`DiskUsageHigh` 噪音九成四，提高阈值或者改成预测型告警（按增长速度）。

**追问**：怎么衡量调整有没有效果？
答：再跑一遍同样的分析：噪音率、每次事故的告警数、检测延迟。这套 SQL 就是为了能重复跑而写的。

## 简历对应

### 简历上写「排查六个服务的 p99 尖峰，定位到连接池耗尽」，会怎么被追问？

**一句话答案**：会被问「你怎么知道是连接池」，我用这个仓库演示完整的证据链。

**展开**：简历上那段是我在公司里的经历，具体数字是公司环境的结果，这个仓库里不复用。这个仓库复现的是同一类问题：trace 里时间在 `db.pool.acquire`，DBStats 显示 InUse 等于上限且 WaitCount 每秒涨五十多，pg_stat_activity 显示连接都是 idle in transaction。仓库实测：同样故障下搜索 p99 从约一万毫秒（被网关超时截断）回到 5.9 毫秒（三轮中位数）。

**追问**：公司里的规模和这里差多少？
答：会如实说这个仓库是笔记本规模、池子故意设小，用来演示方法；公司里的数字我会单独讲，并说明测量方式不同。

### 简历上写「用 pprof 去掉热路径上的过度分配」，怎么用仓库回答？

**一句话答案**：展示 alloc profile 怎么找到排序比较函数，以及微基准和整服务两个数字。

**展开**：线上 profile 里 `rankKey` 和 `fmt.Sprintf` 占 search 约三分之一的分配。修复后微基准从 92 微秒、2953 次分配降到 4.1 微秒、3 次分配；但整个服务每请求分配只从 133 KB 降到 82 KB，约四成。两个数字都讲，只讲二十倍是误导。

**追问**：为什么整服务只降四成？
答：剩下的分配在 JSON 编解码、OTel 和 net/http 里，排序只是其中一块。

### 简历上写「分析六个月的事故和告警数据，按原因排名，写成 runbook」，怎么讲？

**一句话答案**：讲方法（合并重复、按时间关联、按影响排名），并说明仓库用的是合成数据。

**展开**：简历上的分析用的是公司真实数据，结论和数字属于公司。这个仓库用固定种子生成六个月合成数据，复现同样的方法：三千零四十九次告警合并成一千五百一十一个 episode，按总影响排名连接池耗尽第一，而按次数或按告警量都会指向别处。runbook 就是 [docs/runbook.md](runbook.md)，每一步都有能跑的命令和真实输出。

**追问**：你怎么知道你的关联方法准？
答：在合成数据上有真值可以对答案，噪音率误差在三个点以内；在真实数据上只能抽样人工核对，这是方法的局限。
